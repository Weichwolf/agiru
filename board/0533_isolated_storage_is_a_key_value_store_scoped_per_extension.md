# Isolated storage is a key-value store scoped per extension

**Four pages, one item**: isolated storage, the encryption behind its encrypted variant, and the two
key-vault pages that are its cloud counterpart. They are one subject -- where an extension keeps a
secret -- and the encryption page exists to serve the `SetEncrypted` method.

## Five methods and a scope

> "Isolated Storage is a data storage that provides **ISOLATION BETWEEN EXTENSIONS**, so that you can
> keep keys/values in one extension **from being accessed from other extensions.**"
>
> | method | |
> |---|---|
> | `Set(String, String, [DataScope])` | |
> | `Get(String, [DataScope], var Text)` | |
> | `Contains(String, [DataScope])` | |
> | `Delete(String, [DataScope])` | |
> | `SetEncrypted(String, String, [DataScope])` | **"The input string CANNOT EXCEED A LENGTH OF 215 PLAIN CHARACTERS; be aware that SPECIAL CHARACTERS TAKE UP MORE SPACE."** |
>
> The classification is the **`DataScope` option type**.

**The isolation is per EXTENSION**, which is board:0033's app boundary appearing as a data boundary --
and it is the first one in this sweep that is enforced at RUN time rather than by the linker. The
extension's identity has to be available at the call site, and board:0033 says an app is a library, so
the app id is a `constexpr` per translation unit.

**`SetEncrypted`'s 215-character limit is a documented limit and therefore a `static_assert` where the
input is a literal** (board:0081) and a run-time check otherwise. And the note about special
characters says the limit is on the ENCRYPTED length, not the input's character count -- so the check
is on the encoded size.

## The encryption key is one per tenant and lives in a file

> **"Each tenant supports a SINGLE encryption key.** ... generated by the **.NET Framework Data
> Protection API**."
>
> `CreateEncryptionKey` **"fails if the key already exists"**; `ImportEncryptionKey` **"throws a
> warning if a key already exists"**; `DeleteEncryptionKey` clears the state.
>
> **"`EncryptionKeyExists` versus `EncryptionKeyEnabled`"**: the key lives in a FILE; when created or
> imported, **the TENANT TABLE records that encryption is enabled**. **"However, if the encryption
> FILE IS DELETED, then `EncryptionKeyEnabled` CONTINUES TO RETURN TRUE."** `EncryptionKeyExists`
> performs the file-system check.

**Two methods that disagree by design**, and the documentation calls it a best practice to know the
difference. One reads a table, one reads the file system. **An implementation with one method behind
both is wrong in exactly the failure case they exist to distinguish** -- the key is gone and the
tenant still thinks encryption is on.

**The .NET Data Protection API is the key generator in BC**, which agiru does not have. So the key
material is generated differently here -- and that means **encrypted values are not portable between
BC and agiru**, which is a divergence to record rather than a defect: board:0004's CRONUS load would
not be able to decrypt anything BC encrypted.

> **On-premises only.**

## The key vault is the cloud alternative and is out of scope

`devenv-app-key-vault-overview.md` and `devenv-app-key-vault.md` describe an Azure Key Vault an
extension reads secrets from. **That is a cloud bridge**, which `scope.json` excludes, and it is
refused with that as the reason -- the same decision board:0476 takes for Power Automate.

## The choice

A platform table keyed by `{ app id, scope, key }` with a `Text` value, and the extension's app id
supplied by the generator as a `constexpr` per translation unit -- **so the isolation is structural
and not a check somebody can forget.**

`SetEncrypted` encrypts with a per-tenant key; the key lives where board:0032's platform tables live,
and **`EncryptionKeyExists` and `EncryptionKeyEnabled` are two different reads**, as documented.

**Not `libsodium` or a hand-rolled cipher**: CLAUDE.md allows a library where the standard library is
not enough, and this is one -- named with what it replaces when the item is pulled.

## Ordering

Behind board:0032's platform tables and board:0033's app identity. The encryption behind a decision
about a crypto dependency, which has no item yet and is named here.

## Gate, and its negative control

A value set by one app is not readable by another; `SetEncrypted` then `Get` returns the plaintext;
`EncryptionKeyExists` returns false and `EncryptionKeyEnabled` returns true after the key file is
removed.

**The negative control is the cross-app read** -- it must fail, and an implementation that keys only by
`{ scope, key }` returns the other app's secret, which every single-app gate passes.
