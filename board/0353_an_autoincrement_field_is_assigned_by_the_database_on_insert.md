# An `AutoIncrement` field is assigned by the database on insert

> Sets whether the field value should be automatically incremented. **The fields must be of Integer
> or BigInteger.** **The default is false.**
>
> **A table can only contain one auto-increment field.**
>
> The numbers assigned will **not always be consecutive**: deleted records' numbers are not reused,
> and if one of several concurrent transactions is rolled back, **the number it was assigned is not
> reused**.
>
> The `AutoIncrement` property is designed to always assign numbers automatically. **If you want to
> insert a record, be sure that the value in this field is blank before you insert the record.**
>
> If you want to manually assign a value to a field with `AutoIncrement`, **you must be a member of
> the SQL Server `db_owner` permission set**.
>
> **`AutoIncrement` does not work with temporary tables.**

Six rules, and four of them are the ones an implementation gets wrong:

1. **The gap is documented and correct.** A rolled-back transaction burns its number. So a test that
   asserts consecutive entry numbers is asserting something BC does not promise -- and PostgreSQL's
   sequences behave the same way, which makes this the rare case where the two platforms agree by
   construction.
2. **The value is assigned by the DATABASE, not the runtime.** A counter in the process would be
   wrong the moment a second service tier starts, which is CLAUDE.md's "nothing in a process is
   authoritative" exactly.
3. **The assigned value must come BACK.** `Rec.Insert()` leaves the record holding its new number, so
   the insert is `INSERT ... RETURNING`, and board:0087's buffered insert has to reckon with a
   statement whose result the caller needs.
4. **Temporary tables do not have it**, so board:0032's temporary record has to ignore the property
   rather than emulate it.

`AutoIncrement =`: **357 declarations.** These are the `Entry No.` fields of the ledger tables --

## The IST-state

Not in `FieldDef` (`include/meta/TableDef.h:67`). `RuntimeInsert` at `src/rt/Table.cpp:309` stamps the
system fields and writes every value it holds; nothing is left to the database and nothing comes back.
The schema writer at `src/rt/Storage.cpp:94` gives every field a plain column from `ColumnType`, so
an `AutoIncrement` Integer is `integer NOT NULL` and the 357 ledger `Entry No.` fields are written by
the process.

## The choice

One bit on `FieldDef`. The column becomes `GENERATED BY DEFAULT AS IDENTITY` -- `BY DEFAULT` and not
`ALWAYS`, because the page allows a manual assignment under a permission and `ALWAYS` refuses it
outright. The insert omits the column when the field is blank and takes the value back through
`RETURNING`.

**The `db_owner` rule maps onto board:0062's permissions and not onto PostgreSQL's role system**, and
that mapping is this item's open question rather than its answer.

The single-field-per-table rule and the Integer/BigInteger type rule are both `static_assert`s.

## Ordering

A column type in `src/rt/Storage.cpp:94` and a `RETURNING` in `src/rt/Storage.cpp`'s `InsertRow`;
with board:0087, whose insert buffering this changes.

## Gate, and its negative control

Two inserts get two different numbers; a rolled-back insert's number is not reused by the next; the
record holds its number after `Insert()` returns.

**The negative control is the third assertion** -- an implementation that lets the database assign and
never reads the value back passes both of the first two and leaves every ledger entry holding zero.
