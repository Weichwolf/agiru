# A field refuses the values its own declaration refuses, and an AutoIncrement field is the database's

`FieldDef` carries a number, an AL name, a caption, a type and a length. Four documented properties
that DECIDE WHICH VALUES A FIELD ACCEPTS are declared in the AL and reach nothing:

| property | declarations in the read roots | what it says |
|---|---:|---|
| `NotBlank` | **949** | "whether users must enter a value in the selected field" |
| `MinValue` | 897 | "the minimum numeric value for a field" -- Integer, Decimal, Date and Time all have one |
| `MaxValue` | 346 | the maximum |
| `AutoIncrement` | 151 | "whether the field value should be automatically incremented"; Integer and BigInteger only |

`ValidateTableRelation` (457) belongs to the same call site and board:0043 already names it.

**So a value AL refuses is accepted here**, and the failure is the silent-wrong-data class: a
quantity below its minimum, a blank code where the field says it may not be blank. Nothing throws
and the row is written.

## What the platform documents

`properties/devenv-notblank-property.md`, `devenv-minvalue-property.md`,
`devenv-maxvalue-property.md`, `devenv-autoincrement-property.md`.

**`AutoIncrement` is the one that is not a check but a SCHEMA decision.** "If you want to manually
assign a value to a field that has the AutoIncrement property set to true, you must be member of the
`db_owner` database permission set" -- so the value comes from the database, not from AL, and 151
fields in the read roots say so. In PostgreSQL that is `GENERATED BY DEFAULT AS IDENTITY` or a
sequence default, and it has to be decided before the schema is written, like board:0013's system
fields and board:0060's company. It also has to survive `Insert`: the record must read back the
value the database assigned, or every `Entry No.` in the tree is zero.

**Where the checks run is already fixed by board:0043**, and that ordering was measured in the
predecessor rather than reasoned about: the TableRelation check runs BEFORE the `OnValidate`
trigger. `MinValue`, `MaxValue` and `NotBlank` are platform checks of the same kind and run in the
same place -- `Table<Derived>::Validate`, before the trigger, after the assignment.

## What the AL source does

The BaseApp relies on these rather than repeating them: a field declared `MinValue = 0` has no
`OnValidate` asserting it. That is what makes them load-bearing -- there is no second check to
notice they are missing.

## The choice

- **`FieldDef` gains them as `constexpr` data**, beside the relation board:0043 adds: a flag for
  `NotBlank`, an optional minimum and maximum in the field's own type, and an `AutoIncrement` flag.
  All four are knowable at translation time, so all four are `.rodata`.
- **The refusals carry BC's wording** and the code beside it, which is board:0055's mechanism and
  not a new one.
- **`AutoIncrement` reaches the schema and the insert**: the column is an identity column,
  `CreateTable` writes it, and `Insert` reads the assigned value back into the record in the same
  round trip.
- **The minimum and maximum are typed, not numeric.** The documentation gives defaults for Date
  (`January 1, 0`) and Time (`00:00:00`) as well as the numeric types, so a `MinValue` on a Date
  field is a Date -- storing it as a double would be the one thing this tree's invariants forbid.

## Gate

A field with `MinValue = 0` refuses `-1` through `Validate` and accepts `0`; the message is BC's. A
`NotBlank` field refuses the empty value and its own `OnValidate` never runs (board:0043's order). An
`AutoIncrement` field is empty before `Insert` and carries the database's value after it, and two
inserts differ.

**Negative control**: remove the check and require the first case to go red -- and for
`AutoIncrement`, insert twice and require the two rows to collide on the primary key, which is what
a field that is not an identity column does.
